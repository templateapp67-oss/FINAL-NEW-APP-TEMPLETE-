## Canonical authority and identity chain

The only accepted owner authority is:

`auth.users.id → profiles.id → organization_members.user_id (role = owner, active) → organizations.id → salons.organization_id → salon_public_websites.salon_id`

The only accepted authenticated-customer authority is:

`auth.users.id → profiles.id (platform_role = customer unless separately provisioned as an owner) → bookings.customer_id`

`job_salon_members`, URL values, localStorage values, browser-generated IDs, and request body salon IDs are not ownership authority. The browser uses one Supabase client (`src/lib/supabase.ts`) with PKCE, persisted refreshable sessions, and storage key `nexora.auth.qwaehqsmodekbgvnaavz`. Server-side privileged calls use `server/supabaseAdmin.ts`; each HTTP request must first bind the supplied Bearer token to a Supabase Auth user and then preserve that user's tenant/customer identity in the database operation.

## Repair dependency order

1. **Environment and deployment contract:** same-project browser/server validation; pure API entrypoint; production-shaped API smoke.
2. **Schema/migration contract:** explicit canonical manifests; additive M55 compatibility/authorization migration; no live execution without introspection and approval.
3. **Auth/session/routing:** one PKCE exchange owner; customer-vs-owner continuation; nested protected direct URLs.
4. **Authorization/RLS:** actor-bound owner canonical and guest-booking reads/mutations, plus adversarial regressions.
5. **Workspace/profile normalization:** existing and partial account idempotency.
6. **Canonical owner consumers:** real bookings, customers, revenue, calendar, notifications, and DB status mutations.
7. **Public customer flow:** customer Auth continuation, canonical availability/booking, payment, confirmation, My Bookings.
8. **Remove false-success paths:** browser-only booking/payment/offline success in production.
9. **Remaining operational domains:** products, staff, media/content persistence and explicit errors.
10. **Evidence:** full existing tests, new unit/integration/E2E layers, then live existing-account/gateway/deployment journeys when access exists.
